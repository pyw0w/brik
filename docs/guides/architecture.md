# Архитектура и слои

Проект построен вокруг одной жёсткой идеи: **контрибьютор добавляет функционал, не понимая ядра**. Достигается это строгим делением на слои и правилом импортов, которое проверяется статически (`bun run check:boundaries`).

## Три слоя

| Слой | Где живёт | Могут ли его импортировать модули |
|---|---|---|
| **Contract** (публичный контракт) | `src/core/index.ts`, `src/core/testing.ts` | ✅ **да — единственная разрешённая точка входа** |
| **Internal** (реализация ядра) | `src/core/internal/` | ❌ нет |
| **Discord-адаптер** | `src/core/discord/` | ❌ нет |
| **Host** (сборка) | `src/app/`, `src/index.ts` | ❌ нет |
| **Services** (внешние зависимости) | `src/services/` | ✅ да — только `../../core/index.ts`, как и модули |

### Contract

`src/core/index.ts` — курируемый фасад: стабильные типы и фабрики `defineModule`, `defineHandler`, `arg`, `Result`, `Input`, `CommandCatalog`. Это то, что видит каждый модуль. Стабильность гарантируется документацией (ADR-0006) и проверкой границ.

`src/core/testing.ts` — публичные тест-хелперы (`runHandler`, `createInput`, …), их можно импортировать только в тесты.

### Internal

`src/core/internal/` — реализация контракта: `Registry`, `Pipeline`, `store`, `logger`, `config`. **Нестабильна по замыслу** — меняется без гарантий. Модулям недоступна.

### Discord-адаптер

`src/core/discord/` — единственное место, где живёт runtime-зависимость `discord.js` (gateway, registrar, adapter). Благодаря этому контракт не завязан на Discord: `ArgOptionType` — это просто строковый тег, а маппинг на опции Discord делается в registrar-е.

### Host

`src/app/` + `src/index.ts` — сборка приложения: compose, lifecycle, interactor. Здесь тоже нет Discord-типов; дискорд-детали спрятаны в адаптере.

## Правило импортов для модуля

- Код модуля импортирует **только** `'../../core/index.ts'`.
- Тесты модуля — дополнительно `'../../core/testing.ts'`.
- **Никогда** `discord.js` напрямую, `src/core/internal/**` или `src/app/**`.

`bun run check:boundaries` проверяет это статически (входит в CI).

## Как связаны модуль, handler и сервис

```
defineModule (пакет Handler-ов, опции, lifecycle)
 ├── handlers: [defineHandler ...]   → slash-команды / component-хэндлеры кнопок
 ├── services: ['weather']           → декларация внешних зависимостей
 ├── setup / onReady / onShutdown    → жизненный цикл
 └── (экспорт публичных функций)      → API для других модулей

defineService (API-клиент / соединение)
 └── init / close                     → ядро строит и закрывает по жизненному циклу
```

**Handler** — чистая функция: `run(ctx)` принимает `{ input, store, memory, logger, args, services }` и возвращает `Result`. Ядро доставляет Result в канал. Handler не вызывает другие Handler-ы — только публичные функции модулей (ADR-0003).

**Сервис** — именованная глобальная зависимость (API-клиент, соединение). Живёт в `src/services/<name>/service.ts`, объявляется через `defineService`, расширяет типизированный `ServiceMap`. Ядро строит только сервисы, задекларированные включёнными модулями (ADR-0008).

## Поток выполнения команды

1. Slash-команда приходит в адаптер (`src/core/discord/`).
2. Адаптер нормализует её в `Input` (без Discord-деталей).
3. `Pipeline` находит Handler, парсит аргументы (`arg`-схема), применяет дефолты.
4. Прогоняются **предусловия** (`Precondition`): не прошло → короткая ошибка.
5. Проверяются **capabilities** (права Bot-а в канале): нет права → понятная ошибка.
6. Выполняется `run(ctx)` → `Result`.
7. Ядро доставляет `Result` в канал.

## Почему именно так

- **Module** ≠ плагин/фича: самодостаточный пакет, версионируется вместе с ядром (ADR-0004).
- **State** принадлежит ядру (Store, ADR-0002), а не модулю.
- **Capability** — это право Bot-а в канале, а не «фича платформы» (ADR-0001).
- Внешние API/БД — ответственность **сервисов**, не модулей (ADR-0008).

Полная карта решений — в `docs/adr/`.
